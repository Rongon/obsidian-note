# 3. 面试题 · 整个项目中你遇到过的最难的问题是什么

### 一、30 秒口述版（先背这一句）

> 「最难的不是某个技术点，而是一类问题：用户连续操作的时候，后发出去的请求不一定后回来，界面就会显示出和当前筛选条件对不上的内容。我在文章列表上先稳定复现、再定位到这个『返回乱序』，然后用请求取消加序号校验两层解决；后来在评论区的乐观更新里又碰上了同一类问题，就把它收成了一条统一规则。」

### 二、完整版（背景 / 任务 / 行动 / 结果）

**背景 —— 现象**

文章列表支持「分类 + 标签 + 搜索 + 分页」的组合筛选，筛选状态全部放在 URL 里（刷新和前进后退都能还原）。我自己点得快的时候，发现列表内容偶尔和右上角选中的分类对不上。

**任务 —— 我要什么**

先稳定复现，再定位根因，再修，最后让它不再出现。不满足于「再点一下就好了」。

**行动 —— 我具体做了什么**

1. **复现**：本地 localhost 几乎零延迟，怎么点都不出错。把 DevTools 网络节流设成 Slow 4G、再给接口人为加一点延迟，才稳定复现。
2. **定位**：在请求发出和返回处各打一条日志，看到 A 先发后回、B 后发先回——后回来的 A 把 B 的结果覆盖了。
3. **根因**：代码写的是「谁回来就用谁的结果」，但请求的发出顺序和返回顺序本来就没保证。
4. **修第一层**：用 `AbortController`，新请求发出时取消上一个。
5. **修第二层**：每次请求带一个自增序号，回来时比对，不是最新的就直接丢掉。
6. **一个坑**：被取消的请求会抛一个专门的 `CanceledError`，必须单独判断。我一开始把它和网络错误混在一起，用户会莫名看到一个「加载失败」。

**结果 —— 沉淀下来的东西**

快速切换筛选不再错乱；并把这类请求统一收口到一层封装里——凡是「用户操作触发、又会写回列表」的异步请求都走它。后来写评论区的乐观更新时发现是同一类问题（本地先插一条、远端再返回一条，不按 id 去重就会重复），就更坐实了这条规则。

### 三、面试官会追问，你怎么答

| 追问 | 答法 |
|---|---|
| 你怎么保证以后不再犯？ | 不靠小心，靠收口：这类请求统一走同一个封装，新代码没有别的写法 |
| 加个防抖不就行了吗？ | 防抖只能降低频率；用户停一下再点，顺序问题照样在。防抖和这个是两个不同层面的东西 |
| `AbortController` 和序号为什么要两个？ | abort 主要目的是省掉无效请求，同时是第一道防线；序号是兜底，因为 abort 不是瞬间生效，存在「响应已到、回调还没跑」的时间窗 |
| 这个 bug 你怎么测的？ | 人为延迟 + 网络节流 + 快速连点；改完后再把同一套动作跑十几遍确认不再复现 |
| 这和你评论区的乐观更新是什么关系？ | 同一个根问题的两个面孔：异步结果和界面可见状态的一致性 |
| 那你为什么不继续用悲观更新？ | 悲观更新下单次交互的延迟感很明显；乐观更新把体验做好了，代价就是这些一致性问题必须自己兜住，这个取舍我是想清楚的 |
